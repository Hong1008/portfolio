# 이력서 관리

## 원본과 산출물

- `resume.yaml`: 이력서 전용 문장, 노출 순서와 evidence 참조
- `MARKET_REVIEW.md`: 채용 공고·ATS·공개 이력서 검토 기록
- `generated/`: 휴대전화를 제외한 저장소용 DOCX·PDF
- `private.example.yaml`: 제출용 연락처 로컬 설정 예시
- `private.local.yaml`: 실제 제출용 연락처. Git 제외
- `private-output/`: 연락처가 포함된 제출용 DOCX·PDF. Git 제외

이력서 문장은 새로운 사실 원본이 아니다. 경력과 프로젝트 주장은 `src/data/evidence`의 공개 가능하고 확인된 fact 또는 metric을 참조해야 한다.

## 문서 순서

1. 이름·이메일·제출용 휴대전화, 2~3줄 경력 요약과 근거 3개
2. 회사 경력 상세
3. 개인·교육 팀 프로젝트
4. 학력
5. 기술 태그
6. 교육·자격
7. 블로그·GitHub·포트폴리오 링크

회사 경력이 모두 끝나기 전에 개인·교육 프로젝트를 삽입하지 않는다. 모든 경력·프로젝트는 `배경 → 역할 → 주요 성과 → 핵심 구현 → 기술스택 → 한계` 필드를 사용하며, 화면에서는 역할과 주요 성과가 먼저 스캔되도록 강조한다. 학력·기술·교육·자격·링크는 첨부 이력서와 같은 순서로 배치한다.

`주요 성과`와 `핵심 구현`은 한 문단으로 합치지 않고 복수 항목을 허용한다. 서로 다른 결과·구현 판단은 각각 별도 `text`와 `refs`를 가진 배열 항목으로 작성한다.

## 템플릿 구조

- A4 단일 열과 약 13.6mm 바깥 여백을 사용한다.
- 상단에는 `Professional Summary`와 근거 3개를 두며, 숫자는 측정 환경이 연결된 metric만 사용한다.
- 회사·학력·교육 항목은 왼쪽 아이콘 열과 오른쪽 본문 열을 사용한다.
- 회사 프로젝트는 `프로젝트명 → 기간 → 배경 → 역할 → 주요 성과 → 핵심 구현 → 기술스택 → 한계` 순서로 표시한다.
- 회사별 담당 범위와 팀 구성을 프로젝트 앞에 짧게 표시한다.
- 경력 본문은 단일 열을 유지하고, 상단 근거와 하단 자격·링크에만 얕은 3열 요약을 사용한다.
- 사진, 텍스트박스와 수동 페이지 나누기를 사용하지 않는다.
- 회사 경력 뒤의 KExcel·WorkShield 섹션은 현재 확인된 프로젝트를 보존하기 위해 같은 시각 문법으로 확장한 영역이다.

## 작성 규칙

- 결과와 본인 역할을 먼저 쓴다.
- 첫 페이지 요약과 상세 경력에 같은 문장을 반복하지 않는다.
- 팀 결과와 개인 기여를 구분한다.
- 측정 수치는 metric evidence와 측정 범위를 연결한다.
- 근거가 없는 대규모·무중단·고가용성·자동 복구 표현을 사용하지 않는다.
- 경력 공백과 개인 사정에 관한 설명을 추가하지 않는다.
- 이름·연락처·학력은 파싱 가능한 텍스트로 유지하고 사진은 사용하지 않는다.
- 생년월일, 주소, 성별, 희망연봉과 시험 원점수를 추가하지 않는다.
- 수동 페이지 나누기 없이 흐르게 하며, 페이지 수보다 본문 9pt 수준의 글자 크기와 충분한 행간을 우선한다.
- PDF와 DOCX는 상단 정보, 회사·기간과 항목 들여쓰기에 같은 정렬축을 사용한다. 긴 본문을 하나의 셀에 가두거나 중첩 표와 텍스트박스를 사용하지 않는다.

## 생성과 검증

```bash
npm run resume:build
npm run resume:verify
```

제출용 연락처가 필요한 경우 `private.example.yaml`을 `private.local.yaml`로 복사해 값을 입력하고 다음 명령을 실행한다.

```bash
npm run resume:submission
npm run resume:verify:submission
```

시장 검토일로부터 90일이 지났거나 지원 직무가 크게 달라지면 `MARKET_REVIEW.md`를 먼저 갱신한다.
