## 2. 현재 목표

IT·SW 계약서를 표준계약서와 조항 단위로 비교하고 다음을 MCP로 제공한다.

- 대응하는 표준조항 후보
- 별도 확인이 필요한 조항
- 누락 가능성이 있는 표준조항
- 주의 문구 유사 신호
- 관련 법령 원문

검토 범위를 좁히는 도구다.

### 비목표

- 법률 자문
- 위법·합법 판단
- 유·불리 확정
- 계약 안전성 보장
- LLM의 자유로운 최종 법률 판정

안전한 표현:

- 표준 대비 검토 후보와 근거를 제공한다.
- 검색·재정렬·상태 분류 결과를 MCP로 제공한다.

피해야 할 표현:

- 계약서 법률 검토 자동화
- 위법 조항 판정
- 법률 정확도
- 변호사 대체

## 3. 시스템 경계

### 1차 MCP

LLM 없이 다음을 처리한다.

- 문서 파싱
- 조항 분리
- 검색
- 재정렬
- 상태 분류
- 법령 원문 연결

### 선택적 2차 LLM

- 외부 MCP 클라이언트 또는 데모 계층
- 1차 결과를 자연어로 설명
- 서버의 결정론적 검색·분류와 분리

안전한 표현:

- 결정론적 MCP 서버와 선택적 LLM 클라이언트를 분리했다.

### 레이어

```text
contracts
↑
core / adapter
↑
pipe
↑
server
↑
외부 client
```

- contracts: enum, 모델, port
- core: 순수 검색·분류 로직
- adapter: 문서, DB, 검색, 법령과 외부 I/O
- pipe: 런타임 조립과 코퍼스 빌드
- server: FastMCP 표면
- client: 선택적 LLM과 사용자 경험

## 4. 처리 흐름

```text
계약서
→ kordoc 파싱
→ 조항 분리
→ Chroma + BM25 hybrid 검색
→ RRF / rerank
→ NONE / EXTRA / NO_MATCH
→ 전체 표준조항과 역방향 비교
→ MISSING
→ 법령 원문과 MCP 응답
```

### 상태 의미

- NONE: 표준조항과 1차 잠정 매칭
- EXTRA: 근접 후보는 있지만 임계값 미달
- NO_MATCH: 검색 후보 자체가 없음
- MISSING: 표준조항이 사용자 계약서 전체에서 대응되지 않음

### 독소 패턴

- Deviation 상태와 별도의 축
- 알려진 주의 문구와의 유사 신호
- 위법·불공정 확정이 아님
- 빈 배열이 계약 안전성을 의미하지 않음

## 5. RunPod 분리

확인된 구조:

- 운영 Docker 배포는 MCP 단일 컨테이너
- 임베딩과 rerank는 RunPod worker 사용
- 데모 소스는 현재 배포 대상이 아님

안전한 이유 표현:

- 모델 의존성과 GPU 실행 환경을 MCP 애플리케이션에서 분리했다.
- MCP 서버는 문서 처리와 검색 흐름 조립에 집중한다.

피해야 할 표현:

- 비용 절감
- 처리 속도 개선
- 오토스케일링 성과
- GPU 최적화 성과

측정 수치가 없기 때문이다.

## 6. RRF 점수 계약 오류

### 확인된 문제

- RRF 결과 최대 범위는 약 0.0328 수준
- 후속 분류 임계값은 0.5
- 직접 비교하면 어떤 후보도 임계값을 넘을 수 없음

### 테스트가 놓친 이유

- 테스트 대역이 실제 RRF 점수 대신 0.95 같은 값을 반환
- 자료형은 float로 같았지만 값의 의미와 범위가 달랐음
- 모듈 간 점수 계약이 검증되지 않음

### 본인 수행으로 사용할 수 있는 내용

- 실제 실행에서 모든 조항이 매칭 실패하는 현상을 확인했다.
- RRF 점수 범위와 임계값 불일치를 발견했다.
- 점수 기준과 테스트 대역을 실제 실행 특성에 맞게 수정했다.

### 핵심 메시지

- 같은 자료형이어도 값의 생성 방식·범위·의미가 다르면 모듈 간 계약 오류가 발생할 수 있다.
- 테스트 대역은 인터페이스 형태뿐 아니라 실제 값의 특성을 재현해야 한다.

## 7. 평가 구조

### 초기 문제

최종 실행 이후 외부 검색을 다시 수행해 후보와 점수를 수집했다. 외부 모델을 다시 호출하면 실제 판정에 사용된 후보와 평가용 후보가 달라질 수 있었다.

### 변경

- 실제 파이프라인 실행에서 사용한 후보와 점수를 수집
- 실행 trace를 평가 입력으로 사용

안전한 표현:

- 평가 과정에서 검색를 다시 실행하지 않고 실제 판정에 사용한 후보와 점수를 보존했다.

### 골든 데이터

- SI 하도급: 45건
- SM 하도급: 45건
- SW 프리랜서: 45건
- 총 135건

각 유형:

- tuning: 30건
- held-out: 15건

주제 그룹은 split을 넘지 않도록 분리했다.

### 현재 v5 기준선

- Precision: 0.742
- Recall: 0.767
- F1: 0.754
- TP: 69
- FP: 24
- FN: 21
- TN: 21

유형별:

- SI F1: 0.800
- SM F1: 0.781
- SW F1: 0.653

### 지표 해석 제한

- 법률 정확도가 아님
- 전체 계약 안전성 정확도가 아님
- 정해진 골든 데이터에서 1차 조항 대응 상태를 분류한 기준선
- 제품 기본값을 반복 조정하기 위한 테스트셋이 아니라 회귀 검증 기준

### 실험 의사결정

- S 실험
  - tuning F1: 0.563 → 0.462
  - 폐기
- C1 실험
  - SW held-out FN: 4 → 2
  - F1: 0.706 → 0.800
  - FP: 1 → 2
  - 보류

안전한 표현:

- 일부 지표가 개선돼도 사전에 정한 기준과 부작용을 함께 보고 보류하거나 폐기했다.

## 9. 회고 사용 범위

포트폴리오에 사용할 수 있는 학습:

- 검증하기 어려운 법률 의미 판정 기능을 제외하고 1차 MCP의 책임을 재정의했다.
- 실제 실행 후보와 점수를 평가 데이터로 사용했다.
- 실험에 채택·보류·폐기 기준이 필요하다는 점을 적용했다.
- 설계 결과보다 문제와 근거를 팀과 공유하는 과정이 중요하다는 점을 배웠다.

본문에서 직접적으로 쓰지 않을 내용:

- AI가 주도권을 가졌다는 표현
- AI 제안을 충분히 이해하지 못했다는 긴 자기비판
- 거의 혼자 개발했다는 표현
- 팀원에 대한 책임 전가
- 감정적인 프로젝트 평가
