## 2. 통합 결제 API

### 실제 처리 흐름

1. 주문 요청
   - `requestOrder`
   - `usp_request_order`
   - 요청 주문과 주문키 생성
2. PG 준비
   - 외부 PG ready 호출
   - Redis에 요청 정보 캐시
3. 구매 처리
   - `purchase`
   - `usp_purchase_order`
   - PURCHASED 상태
4. 완료 처리
   - `complete`
   - `usp_complete_order`
   - 재화 제공 후 COMPLETED
5. 인앱 결제
   - 앱스토어 영수증 검증
   - `usp_in_app_purchase_order`

### 상태

- REQUESTED
- PURCHASED
- COMPLETED

목적:

- 외부 승인과 내부 재화 제공을 분리해 추적
- 승인 후 내부 반영이 미완료된 주문 식별

### 중복 처리 방어

PG 승인:

- PG사 자체 중복 승인 방어
- DB 주문 상태 검증

인앱 영수증:

- Redis 사전 확인
- 단일 JVM에서 `synchronized(this)` 적용
- 다중 WAS에서는 같은 영수증 검증이 동시에 진행될 가능성이 있음
- 최종적으로 DB의 결제 트랜잭션 식별키 UNIQUE 제약이 중복 재화 지급을 방지

안전한 표현:

- DB 상태 검증과 영수증 식별키 UNIQUE 제약으로 중복 승인 반영 및 중복 재화 지급을 방지했다.

피해야 할 표현:

- 완전한 분산 동시성 제어
- Redis 락을 통한 중복 방지
- Exactly-once 결제
- 모든 중복 요청 차단

### 복구 배치

- Redis PURCHASED 정보 TTL: 약 300초
- TTL이 약 130초 이하로 남은 주문을 복구 대상으로 조회
- 결제 승인 후 재화 제공이 완료되지 않은 주문을 재처리
- ShedLock으로 다중 WAS의 복구 배치 중복 실행을 방지

안전한 명칭:

- 결제 승인 후 재화 제공 미완료 주문 재처리
- 미완료 주문 복구 배치

피해야 할 명칭:

- 결제 유실 자동 복구
- 모든 결제 실패 자동 복구
- 승인 누락 복구 시스템

### 처리 가능한 실패

- DB에 PURCHASED 상태가 저장됨
- 재화 제공 또는 COMPLETE 처리가 완료되지 않음
- Redis 캐시가 남아 있음
- 복구 배치가 주문을 다시 처리할 수 있음

### 처리하지 못한 실패

- PG 승인은 성공했지만 DB의 PURCHASED 저장 자체가 실패한 경우
- 이 경우 Redis와 DB 상태가 REQUESTED에 남을 수 있음
- 서비스 중단이 TTL보다 길어 Redis 정보가 만료된 경우
- Redis 캐시가 유실된 경우
- 외부 결제 상태와 내부 DB를 정기적으로 대조하는 reconciliation은 없음

### 확인된 구현 문제

- 복구 배치 반복문에서 특정 조건에 `continue`가 아닌 `return`을 사용해 뒤 주문 처리가 중단될 수 있는 문제가 있었다.

포트폴리오에 사용할 경우:

- 복구 범위를 검토하는 과정에서 반복문 조기 종료로 이후 주문을 처리하지 못할 수 있는 조건을 확인했다.

당시 수정 여부가 불확실하면 `수정했다`고 단정하지 않는다.

### 플랫폼별 구현

Google Play:

- 영수증 검증
- 구독 연장 처리
- 구매 확인 처리

Apple:

- 인앱 결제 영수증 검증

안전한 표현:

- Google Play 구독 연장과 구매 확인, Apple 인앱 결제 영수증 검증을 구현했다.

피해야 할 표현:

- Google과 Apple 모두 동일한 구독 갱신 로직 구현
- 위변조를 완전히 차단
- 영수증 검증으로 모든 사기 결제 방지

### 공개 범위

사용자 확인:

- 현재 서비스가 종료돼 시스템명과 상세 구조 공개 가능

공개 가능:

- 회사명과 서비스명
- 상태 흐름
- Redis TTL
- Stored Procedure 연동
- Google Play·Apple 처리 범위
- DB UNIQUE 제약
- ShedLock

공개하지 않음:

- 실제 결제키
- 사용자 영수증
- PG 인증 정보
- 내부 DB 스키마 전문
- 회사 코드 원문

### 미래 설계 제외

Outbox 또는 상태 이벤트 기반 재설계는 LLM 권장 사항이며 사용자 본인의 구현·판단이 아니다. 포트폴리오 본문에 넣지 않는다.
