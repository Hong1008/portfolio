## 3.2 온보딩 메일 발송 시스템

### 확인된 문제

- 기존 네이버웍스 메일 API는 서버에서 대량·일괄 발송하는 구조에 적합하지 않았다.
- 배치가 중단되거나 다시 실행될 수 있었다.
- SQS 메시지는 중복 전달될 수 있었다.
- 대상자 선별과 실제 전송의 책임을 분리할 필요가 있었다.

### 본인 수행

- 네이버웍스 API 대신 AWS SES를 사용하도록 전환했다.
- 대상자 선별을 담당하는 배치 서버와 실제 전송을 담당하는 메일 서버를 SQS로 분리했다.
- 배치 재실행 중복을 방지하기 위해 발송 기준일을 포함한 DB UNIQUE 제약을 사용했다.
- SQS 메시지 중복 전달에 대응하기 위해 메일 트랜잭션 키에 DB UNIQUE 제약을 사용했다.
- 온보딩 상태 추적과 실제 메일 발송 조건을 분리했다.
- 같은 발송 구조를 인보이스 메일에도 재사용했다.

### 핵심 구조

```text
배치 서버
- 발송 대상자 선별
- 발송 요청 기록
- SQS 메시지 발행

메일 서버
- SQS 메시지 소비
- 트랜잭션 키 중복 확인
- SES 전송
```

### 멱등성 범위

1. 배치 재실행 단계
   - 발송 기준일과 대상 기준의 UNIQUE 제약
2. 메시지 소비 단계
   - 메일 트랜잭션 키의 UNIQUE 제약

`2단 멱등성`은 위 두 단계의 중복 방어를 의미한다.

### 사용할 수 있는 결과 표현

- 배치 재실행과 메시지 중복 전달을 서로 다른 DB 제약으로 방어했다.
- 대상자 선별과 메일 발송의 책임을 분리했다.
- 같은 발송 구조를 인보이스 메일에 재사용했다.

### 사용하면 안 되는 표현

- 실패율 0%
- 메일 유실 0%
- 자동 복구 시스템
- 대규모 트래픽 처리
- 서버 부하를 획기적으로 분산
- Exactly-once 전송 보장

### 공개 범위

공개 가능:

- SES/SQS 사용
- 배치와 메일 서버 역할
- DB UNIQUE 기반 중복 방지
- 온보딩·인보이스 재사용

공개하지 않음:

- 실제 사용자 정보
- AWS 계정, 큐 이름, 내부 URL
- 운영 발송량
- 비용 수치
- 회사 내부 코드

## 3.3 점검 보고서 생성 구조 개선

### 확인된 문제

- Apache POI 기반 점검 보고서 생성에서 지연이 발생했다.
- 보고서별로 Workbook, Sheet, Row, Cell 처리 코드가 반복됐다.
- 라이브러리 종속 코드가 보고서 로직에 노출됐다.

### 본인 수행

- 성능 문제를 개선하기 위해 FastExcel 기반 생성 방식으로 전환했다.
- Kotlin DSL을 사용해 반복되는 보고서 생성 흐름을 공통 빌더로 분리했다.
- 엑셀 라이브러리 종속 코드를 공통 영역으로 제한했다.

### 회사 업무와 KExcel의 경계

회사 업무에서는 Kotlin DSL을 사용한 공통 빌더를 구현했다. 구체적인 DSL 구조는 확인된 범위를 넘어 확장하지 않는다.

다음은 KExcel 개인 프로젝트의 결과이며 회사 성과로 표현하지 않는다.

- `ExcelDriver` 인터페이스
- POI/FastExcel 엔진 교체
- JMH 벤치마크
- 동시 쓰기 Fail-Fast
- JitPack 공개
- 병합 성능 최적화 수치

### 수치 사용 제한

회사 운영 환경의 `30초 → 3초` 수치는 당시 로그 또는 측정 근거가 확인되지 않았다. 회사 경력에는 사용하지 않는다.

### 안전한 결과 표현

- POI 기반 생성 방식에서 FastExcel로 전환했다.
- 보고서 생성 흐름과 라이브러리 종속 영역을 분리했다.
- 보고서별 반복 구현을 줄일 수 있는 공통 구조를 만들었다.

## 5.2 통합 결제 API

### 실제 처리 흐름

1. 주문 요청
   - `requestOrder`
   - `usp_request_order`
   - 요청 주문과 주문키 생성
2. PG 준비
   - 외부 PG ready 호출
   - Redis에 요청 정보 캐시
3. 구매 처리
   - `purchase`
   - `usp_purchase_order`
   - PURCHASED 상태
4. 완료 처리
   - `complete`
   - `usp_complete_order`
   - 재화 제공 후 COMPLETED
5. 인앱 결제
   - 앱스토어 영수증 검증
   - `usp_in_app_purchase_order`

### 상태

- REQUESTED
- PURCHASED
- COMPLETED

목적:

- 외부 승인과 내부 재화 제공을 분리해 추적
- 승인 후 내부 반영이 미완료된 주문 식별

### 중복 처리 방어

PG 승인:

- PG사 자체 중복 승인 방어
- DB 주문 상태 검증

인앱 영수증:

- Redis 사전 확인
- 단일 JVM에서 `synchronized(this)` 적용
- 다중 WAS에서는 같은 영수증 검증이 동시에 진행될 가능성이 있음
- 최종적으로 DB의 결제 트랜잭션 식별키 UNIQUE 제약이 중복 재화 지급을 방지

안전한 표현:

- DB 상태 검증과 영수증 식별키 UNIQUE 제약으로 중복 승인 반영 및 중복 재화 지급을 방지했다.

피해야 할 표현:

- 완전한 분산 동시성 제어
- Redis 락을 통한 중복 방지
- Exactly-once 결제
- 모든 중복 요청 차단

### 복구 배치

- Redis PURCHASED 정보 TTL: 약 300초
- TTL이 약 130초 이하로 남은 주문을 복구 대상으로 조회
- 결제 승인 후 재화 제공이 완료되지 않은 주문을 재처리
- ShedLock으로 다중 WAS의 복구 배치 중복 실행을 방지

안전한 명칭:

- 결제 승인 후 재화 제공 미완료 주문 재처리
- 미완료 주문 복구 배치

피해야 할 명칭:

- 결제 유실 자동 복구
- 모든 결제 실패 자동 복구
- 승인 누락 복구 시스템

### 처리 가능한 실패

- DB에 PURCHASED 상태가 저장됨
- 재화 제공 또는 COMPLETE 처리가 완료되지 않음
- Redis 캐시가 남아 있음
- 복구 배치가 주문을 다시 처리할 수 있음

### 처리하지 못한 실패

- PG 승인은 성공했지만 DB의 PURCHASED 저장 자체가 실패한 경우
- 이 경우 Redis와 DB 상태가 REQUESTED에 남을 수 있음
- 서비스 중단이 TTL보다 길어 Redis 정보가 만료된 경우
- Redis 캐시가 유실된 경우
- 외부 결제 상태와 내부 DB를 정기적으로 대조하는 reconciliation은 없음

### 확인된 구현 문제

- 복구 배치 반복문에서 특정 조건에 `continue`가 아닌 `return`을 사용해 뒤 주문 처리가 중단될 수 있는 문제가 있었다.

포트폴리오에 사용할 경우:

- 복구 범위를 검토하는 과정에서 반복문 조기 종료로 이후 주문을 처리하지 못할 수 있는 조건을 확인했다.

당시 수정 여부가 불확실하면 `수정했다`고 단정하지 않는다.

## 7.3 벤치마크

### 측정 환경

- JVM: OpenJDK 21, Adoptium
- Heap: 512MB
- GC: G1GC
- JMH: 1.36
- FastExcel: 0.18.4
- Apache POI: 5.2.5, SXSSF

README의 최신 의존 버전과 벤치마크 당시 버전은 다를 수 있다. 포트폴리오에는 `벤치마크 당시 버전`이라고 명시한다.

### DSL 오버헤드

조건:

- 10,000행 × 10열
- Native API와 DSL 처리량 비교

결과:

- FastExcel Native: 8.932 ops/s
- FastExcel DSL: 8.653 ops/s
- FastExcel DSL 오버헤드: 3.1%
- POI Native: 4.878 ops/s
- POI DSL: 4.856 ops/s
- POI DSL 오버헤드: 0.4%

### 핫패스 최적화

변경:

- inline 함수 적용
- 핫루프 내 `runCatching` 제거
- 반복 람다 생성 감소
- 수동 락 제어

결과:

- FastExcel DSL 오버헤드: 16.3% → 3.1%
- 실행당 DSL 추가 메모리 할당량: 약 200KB → 약 364B
- 추가 할당량 기준 약 99.8% 감소

주의:

- 전체 JVM 메모리 사용량 99.8% 감소가 아니다.
- DSL 추가 할당량의 감소다.
- `셀당 364B`로 표현하지 않는다.

### 대용량 처리

- 100,000행
  - FastExcel: 0.238초
  - POI SXSSF: 0.440초
- 1,000,000행
  - FastExcel: 3.396초
  - POI SXSSF: 4.249초

안전한 표현:

- 512MB heap의 벤치마크에서 100만 행 생성을 완료했다.
- 해당 환경에서 FastExcel이 POI SXSSF보다 빠르게 측정됐다.

피해야 할 표현:

- 모든 환경에서 100만 행 3초
- 메모리 사용량이 데이터 크기와 완전히 무관
- 운영 환경 성능

### 병합 성능

문제:

- POI `addMergedRegion`이 병합 추가마다 기존 영역과의 중복을 검사
- 병합 개수 증가 시 O(n²) 검증 비용

변경:

- `addMergedRegionUnsafe()` 사용

결과:

- 처리량: 3.36 → 17.42 ops/s
- GC 할당 속도: 1580.8 → 328.6 MB/s

한계:

- 중복 병합 검증을 우회하므로 잘못된 병합 요청을 사전에 방지할 전제가 필요
- 병합 메타데이터는 파일 작성 완료 시점까지 메모리에 유지
- CPU 병목은 줄었지만 memory residency는 남음

안전한 표현:

- POI 병합 검증 병목을 분석하고 Driver 구현에서 우회해 처리량을 개선했다.

피해야 할 표현:

- 전체 엑셀 생성 속도 518% 개선
- 안전성이 전혀 손상되지 않는 최적화
- OOM 완전 해결

## 8.4 처리 흐름

```text
계약서
→ kordoc 파싱
→ 조항 분리
→ Chroma + BM25 hybrid 검색
→ RRF / rerank
→ NONE / EXTRA / NO_MATCH
```

- Deviation 상태와 별도의 축

- 위법·불공정 확정이 아님

## 8.6 RRF 점수 계약 오류

### 확인된 문제

- RRF 결과 최대 범위는 약 0.0328 수준
- 후속 분류 임계값은 0.5
- 직접 비교하면 어떤 후보도 임계값을 넘을 수 없음

### 테스트가 놓친 이유

- 테스트 대역이 실제 RRF 점수 대신 0.95 같은 값을 반환
- 자료형은 float로 같았지만 값의 의미와 범위가 달랐음
- 모듈 간 점수 계약이 검증되지 않음

### 본인 수행으로 사용할 수 있는 내용

- 실제 실행에서 모든 조항이 매칭 실패하는 현상을 확인했다.
- RRF 점수 범위와 임계값 불일치를 발견했다.
- 점수 기준과 테스트 대역을 실제 실행 특성에 맞게 수정했다.

### 핵심 메시지

- 같은 자료형이어도 값의 생성 방식·범위·의미가 다르면 모듈 간 계약 오류가 발생할 수 있다.
- 테스트 대역은 인터페이스 형태뿐 아니라 실제 값의 특성을 재현해야 한다.

## 8.7 평가 구조

### 초기 문제

최종 실행 이후 외부 검색을 다시 수행해 후보와 점수를 수집했다. 외부 모델을 다시 호출하면 실제 판정에 사용된 후보와 평가용 후보가 달라질 수 있었다.

### 변경

- 실제 파이프라인 실행에서 사용한 후보와 점수를 수집
- 실행 trace를 평가 입력으로 사용

안전한 표현:

- 평가 과정에서 검색을 다시 실행하지 않고 실제 판정에 사용한 후보와 점수를 보존했다.

### 골든 데이터

- SI 하도급: 45건
- SM 하도급: 45건
- SW 프리랜서: 45건
- 총 135건

각 유형:

- tuning: 30건
- held-out: 15건

주제 그룹은 split을 넘지 않도록 분리했다.

### 현재 v5 기준선

- Precision: 0.742
- Recall: 0.767
- F1: 0.754
- TP: 69
- FP: 24
- FN: 21
- TN: 21

유형별:

- SI F1: 0.800
- SM F1: 0.781
- SW F1: 0.653

### 지표 해석 제한

- 법률 정확도가 아님
- 전체 계약 안전성 정확도가 아님
- 정해진 골든 데이터에서 1차 조항 대응 상태를 분류한 기준선
- 제품 기본값을 반복 조정하기 위한 테스트셋이 아니라 회귀 검증 기준

### 실험 의사결정

- S 실험
  - tuning F1: 0.563 → 0.462
  - 폐기
- C1 실험
  - SW held-out FN: 4 → 2
  - F1: 0.706 → 0.800
  - FP: 1 → 2
  - 보류

안전한 표현:

- 일부 지표가 개선돼도 사전에 정한 기준과 부작용을 함께 보고 보류하거나 폐기했다.
